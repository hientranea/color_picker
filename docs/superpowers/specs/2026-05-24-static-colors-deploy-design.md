# Static `/colors` Pages on GitHub Pages — Design Spec

**Date:** 2026-05-24
**Branch:** `feature/colors-static-export`
**Status:** Draft — pending user review

## Goal

Make the `/colors` color-meaning pages (currently on the `meaning` branch with a dynamic Supabase + ISR + API-routes + edge-OG architecture) deployable to GitHub Pages alongside the existing landing page and `/palettes`, without introducing a second host. Preserve full SEO surface by pre-rendering one HTML file per color at build time.

## Non-goals (out of scope for this spec)

- Refactoring `/palettes` to render palette content server-side for SEO. (Known issue: `/palettes` is `"use client"` with React Query, so the static HTML the crawler sees is the loading skeleton, not real palette content. Worth fixing later.)
- Hosting a real public REST API for external consumers. The legacy `/api/colors*` routes will be replaced by static JSON files for shape compatibility, not by a live API.
- Per-color dynamic Open Graph images. Replaced with a single static OG image for all color pages.
- Merging anything to `main`. All work lands on the `feature/colors-static-export` branch; the human user merges manually after verification.

## Architecture

Single Next.js application, fully static-exported (`output: 'export'`), deployed to GitHub Pages via the existing `.github/workflows/publish.yml`. No runtime server, no Vercel, no proxy, no second host. Same domain (`colorone.site`).

The `/colors` data flow is split between build time and request time:

- **Build time (in CI and locally):** A Node script (`scripts/snapshot-colors.mjs`) connects to Supabase via env vars, reads the `color_psychology_data` table, and writes a JSON snapshot to `app/colors/data/colors.snapshot.json`. The snapshot is committed to git — so dev/build works offline if Supabase env vars are missing or the Supabase project is down. The snapshot file is regenerated by the script before each `next build` (wired as a `prebuild` npm hook).
- **Build time (during `next build`):** `app/colors/[color_name]/page.tsx` is a Server Component. Its `generateStaticParams` enumerates every slug from the snapshot, and Next.js renders one HTML file per color into `out/colors/<slug>/index.html`. `dynamicParams = false` so unknown slugs 404 at build (not runtime).
- **Build time (just before export):** The snapshot script also writes `out/api/colors.json` and `out/api/colors/<slug>.json` as static JSON files, mirroring the legacy API URL shape minus query parameters, rate limiting, and on-demand caching.
- **Request time (GitHub Pages):** GH Pages serves static HTML and static JSON. No Supabase, no Node, no edge runtime, no ISR, no dynamic routes. First byte is real content.

Trade lived with: data updates require a rebuild. The existing workflow runs on push to `main` and via `workflow_dispatch`; that covers all expected use cases since color psychology content is hand-curated and changes rarely. A future Supabase webhook → GH Action trigger is possible but unnecessary for v1.

## File-level change set

### Create

- `scripts/snapshot-colors.mjs` — Node ESM script. Reads `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` from env (or `.env.local` via `dotenv/config`). Calls `select *` on `color_psychology_data`. Sanitizes JSONB fields (replicating `ensureObject` / `ensureArray` from `meaning`'s `colorDataService.ts`). Writes:
  - `app/colors/data/colors.snapshot.json` — full array of color records, committed.
  - `public/api/colors.json` — list-page projection: `[{ slug, color_name, hex_code, emotional_associations }, ...]`.
  - `public/api/colors/<slug>.json` — one file per color, full record.
- `app/colors/data/colors.snapshot.json` — committed snapshot (initial run produces this).
- `public/api/colors.json` and `public/api/colors/<slug>.json` — committed alongside the snapshot for reproducibility; regenerated by the script.
- (No new image asset needed.) Color-page metadata reuses the existing `/public/hero-advance-harmony.png` (1200×630, already used by `/palettes`) as the single OG image. Plan may swap to a different existing asset if visually preferable, but no new image creation is in scope.

### Modify

- `next.config.mjs` — set `output: 'export'`, add `images: { unoptimized: true }` (required for static export since Next's image optimizer needs a server), keep `basePath: ""` and `reactStrictMode: true`. Drop the misleading `distDir: "out"` line — with `output: 'export'`, Next writes the static export to `out/` by default; the `distDir` directive actually controls the *intermediate* build folder (`.next` by default) and should not be `out`.
- `app/colors/utils/colorDataService.ts` — replace the Supabase server-client calls with synchronous reads from `colors.snapshot.json`. Same exported signatures (`getAllColors`, `getColorBySlug`, `getAllColorSlugs`, `getAllColorNames`, `colorNameToSlug`, `slugToColorName`) so the page/component callers don't change. All functions become synchronous — `async` may be kept on the signature for minimal callsite churn, but the implementation does no I/O.
- `app/colors/[color_name]/page.tsx` — drop `export const revalidate = 3600`. Change `generateStaticParams` from `() => []` to return every slug from the snapshot. Add `export const dynamicParams = false`. Keep the rest of the page logic as-is.
- `app/colors/[color_name]/metadata.ts` — replace the dynamic `/api/og?color=...&name=...` OG URL with the existing static `/hero-advance-harmony.png` for both `openGraph.images` and `twitter.images`. Keep the rest of the metadata generation (title, description, keywords from emotional_associations).
- `app/colors/page.tsx` — keep as a Server Component, but `getAllColors()` now returns from snapshot synchronously. The page already renders palette content in HTML; no structural change needed.
- `utils/supabase.ts` — for the build-time script's use. Replace the hardcoded URL+anon key (currently committed in source, a soft security smell) with reads from `process.env.NEXT_PUBLIC_SUPABASE_URL` and `process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY`. The function `createSupabaseServerClient` stays available for the snapshot script; runtime pages don't call it after the rewrite.
- `package.json` — add scripts:
  - `"snapshot:colors": "node scripts/snapshot-colors.mjs"`
  - `"prebuild": "pnpm run snapshot:colors"` (so `next build` is preceded by snapshotting in dev and CI).
- `.github/workflows/publish.yml` — pass `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` from repo secrets into the build step. Add `permissions: contents: read` (already present). The `pnpm next build` step runs unchanged because `prebuild` triggers automatically; alternatively, change to `pnpm build` to be explicit.

### Delete (only after the static JSON replacements exist and pages no longer reference them)

- `app/api/colors/route.ts`
- `app/api/colors/[slug]/route.ts`
- `app/api/og/route.tsx`
- `app/api/` directory if it becomes empty.

These files exist on the `meaning` branch and are copied over to `feature/colors-static-export` unchanged or with minimal adjustment:

- `app/colors/[color_name]/page.tsx` (modified per above)
- `app/colors/[color_name]/metadata.ts` (modified per above)
- `app/colors/page.tsx` (modified per above)
- `app/colors/layout.tsx` (as-is)
- `app/colors/metadata.ts` (as-is)
- `app/colors/components/*.tsx` (9 components, as-is)

## Build pipeline

The existing `.github/workflows/publish.yml` becomes:

```
checkout → setup pnpm → setup node → setup-pages → restore cache → pnpm install → pnpm build → upload artifact → deploy
```

The only structural change is the env-var pass-through. Concretely:

```yaml
- name: Build with Next.js
  env:
    NEXT_PUBLIC_SUPABASE_URL: ${{ secrets.NEXT_PUBLIC_SUPABASE_URL }}
    NEXT_PUBLIC_SUPABASE_ANON_KEY: ${{ secrets.NEXT_PUBLIC_SUPABASE_ANON_KEY }}
  run: pnpm build
```

`pnpm build` invokes `prebuild` (which runs `snapshot:colors`) and then `next build`. With `output: 'export'`, Next writes static assets to `out/`, which the existing `actions/upload-pages-artifact@v3` step already targets.

Repo secrets `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` must be added in GitHub before the first CI run.

## SEO considerations

Each `/colors/<slug>` page is now a real static HTML file that crawlers can index with no JS execution required. The structured-data component (`ColorStructuredData`) continues to emit JSON-LD into the page body. Internal linking from `/colors` index → individual color pages → `RelatedColors` already exists.

Sitemap: the existing `public/sitemap.xml` should be regenerated at build time by the snapshot script (or a follow-up step) to include every `/colors/<slug>` URL. Optional for v1, but cheap to add.

Canonical URLs: the `generateMetadata` function already produces full URLs using `NEXT_PUBLIC_SITE_URL`; ensure that env var is set in CI as well.

OG image: every color page references `/og/colors-default.png`. Lower social-share quality than dynamic per-color OG, but consciously chosen for simplicity.

## Risks and mitigations

- **Build time scales with color count.** At hundreds of colors, build time grows by tens of seconds. At thousands, single-digit minutes. Both fit comfortably in GH Actions' free-tier limits.
- **Stale data between rebuilds.** Acceptable for hand-curated content. Mitigation: a manual `workflow_dispatch` rebuild after data edits.
- **Snapshot drift if commit is forgotten.** The snapshot is regenerated on every CI build, so what gets deployed always reflects the current Supabase state. A locally stale snapshot only affects developer machines.
- **Supabase RLS or schema changes break the script silently.** The snapshot script should fail loudly (non-zero exit) on Supabase errors, so CI catches it before deploy.
- **Hardcoded Supabase URL+anon key in `utils/supabase.ts` survive the rewrite.** Flagged for replacement with env vars during the work (not a separate effort).

## Migration plan

All work happens on `feature/colors-static-export`. The branch is already created off the latest `main`.

Order of operations (high-level — detailed steps go in the implementation plan):

1. Wire env-var support in `utils/supabase.ts` (no behavioral change yet for callers).
2. Author `scripts/snapshot-colors.mjs`. Run locally; verify output JSON. Commit the initial snapshot.
3. Update `next.config.mjs` (`output: 'export'`, `images.unoptimized`, remove `distDir: "out"`).
4. Port `app/colors/*` components + utils + layout + metadata from `meaning` to the feature branch unchanged. Verify imports resolve.
5. Modify `app/colors/utils/colorDataService.ts` to read from snapshot. Modify `app/colors/[color_name]/page.tsx` (`generateStaticParams`, drop `revalidate`, add `dynamicParams = false`).
6. Modify `app/colors/[color_name]/metadata.ts` to use the static OG image.
7. Delete `app/api/*` routes and the directory.
8. Add `snapshot:colors` and `prebuild` to `package.json`.
9. Run `pnpm build` locally end-to-end. Verify `out/colors/<slug>/index.html` exists for representative slugs. Verify the page HTML contains real color content (not a loading skeleton), structured-data JSON-LD, and the canonical OG image URL.
10. Update `.github/workflows/publish.yml` to pass Supabase env from secrets.
11. Add the two Supabase repo secrets in GitHub Settings (manual step for the user; documented in the plan).
12. Push the branch. The workflow runs against the feature branch only via `workflow_dispatch` (the trigger config can be temporarily extended to include the feature branch for testing — to be removed before merge).
13. Human user manually reviews the deployed preview and merges to `main` when satisfied.

## Testing strategy

Local verification (each step a hard pass/fail):

- `pnpm snapshot:colors` exits 0 and produces non-empty `colors.snapshot.json` with the expected shape.
- `pnpm build` exits 0 with no warnings about dynamic features (no `revalidate`, no API routes, no `Dynamic server usage` errors).
- `out/colors/index.html` exists and lists every color.
- `out/colors/<known-slug>/index.html` exists for at least 5 sample slugs. Verified by `grep` for the color name and hex code in the rendered HTML.
- `out/api/colors.json` and `out/api/colors/<sample-slug>.json` exist and parse as valid JSON.
- `out/api/` does not contain anything that looks like a Next.js server route (no `route.js`).
- `pnpm start` is NOT used (we only test the static export, not the dev server).
- Static export served locally via `npx serve out` renders every color page correctly — links, structured data, metadata, OG image references all resolve to relative URLs that exist in `out/`.

CI verification (after pushing the feature branch):

- The GitHub Action completes green.
- The deployed preview (gh-pages of the feature branch, or wherever the workflow exposes the artifact) shows working `/colors/<slug>` pages with first-byte HTML containing the color content.
